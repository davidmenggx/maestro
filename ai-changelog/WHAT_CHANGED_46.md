WHAT CHANGED 46: WORLD LAG WHILE SILENT, TRACE AND TIMING FIXES

Summary
`world.lag` is now set for every node each tick from its last heartbeat, not only when a heartbeat arrives, so a holder that goes silent shows its lag growing. The heartbeat field `search_micros` is renamed `worker_micros`, since it is worker time with encoding included; the answer's `search_micros` keeps its name and is now 0 when the node did not search. The controller no longer adds answers at sequence 0 to `node.search.micros`. A finished trace that has an answer but no send yet is held back one flush, so a stream-mode send handed over a hand-over late still lands in its trace. A trace id's low half is now a hash of the request id rather than the id itself. The stage spans `batch.wait` and `encode` are renamed `dispatch.wait` and `send.wait`. The span export queue now reports its drops as metrics. `Tracing.NONE`, the default `Timing` argument of `encodeResponse`, and a shadowed variable in `NodeCore::run` are gone. This supersedes the trace id format and span names given in entry 45.

Decisions made without explicit instruction
- The heartbeat field was renamed, not the answer's. The heartbeat value is worker time (search plus encode), which is how the spec already words it; the answer's value really is search time. The wire layout is unchanged, as FlatBuffers matches fields by slot. Making the two measure the same thing was not possible: an answer cannot carry its own encode time.
- The node reports `search_micros` 0 for a request it did not search, and the controller also skips sequence 0 answers. Both are cheap, and either alone would leave the model or the node inconsistent.
- Lag is read at `TickBegan`, after the hand-over, from each node's last heartbeat. A holder with no report naming its region is skipped, as before. The last report is kept across a lost link, so a lost holder's lag grows until its region is handed off. A healthy holder now shows a sawtooth of up to one heartbeat interval (1 s) of frames. The alternative, treating a holder with no report as having applied nothing, would spike on every new link.
- A trace with an answer and no send is held back one flush only, not until its send arrives, so a send that never comes cannot hold a trace forever.
- The trace id's low half is the request's draw from a SplitMix64 stream seeded by the run. It is not the hash the controller samples by, so a downstream sampler sees no pattern in the traces it is given. A trace can no longer be read off its id; it is found by the `maestro.request.id` attribute. The alternative was to keep the plain id and document that traces must not be sampled downstream.
- The span stages were renamed, not split. `send.wait` covers encoding and, in batch mode, the wait for the hand-over that sends it. Splitting it would need one more timestamp per trace.
- The `BatchSpanProcessor` is given the meter provider, so it exports `processedSpans` (with `dropped`) and `queueSize`. Capping the sample rate or building spans off the server thread were the alternatives; the config now notes that a high rate suits short trials only.
- The stalled-holder lag test now stalls at tick 25, after the owner's first heartbeat, since a holder that has never reported has no lag to show.
